# TESO Fisher — Screenshot Capture and Test Image Data

## Назначение документа

Этот документ описывает, как в проекте TESO Fisher устроен захват экрана и как реальные screenshots превращаются в
тестовые данные.

Документ особенно полезен при возвращении к проекту после длительного перерыва, потому что здесь собраны в одном месте
три связанные, но разные вещи:

1. инструмент для ручного создания новых изображений для тестов;
2. runtime-код, который делает screenshot во время работы приложения;
3. механизм, с помощью которого тесты используют заранее сохранённые JPEG вместо реального экрана.

Главная идея: **production-код захватывает экран в памяти, а тесты обычно работают с заранее сохранёнными изображениями
**. Поэтому запуск тестов не требует запущенной ESO.

---

## 1. Где находится код

### 1.1. Скрипт для создания новых тестовых screenshots

```text
 tests/data_screen_capture/create_new_data.py
```

Это отдельный вспомогательный скрипт для ручного сбора изображений.

Текущая реализация:

```python
import time

from PIL import ImageGrab


while True:
    time.sleep(1)
    capture = ImageGrab.grab()
    capture.save(
        f"{time.ctime(time.time()).replace(':', '_')}.jpeg",
        format="JPEG"
    )
```

### Что он делает

Скрипт бесконечно повторяет следующую последовательность:

```text
ждать 1 секунду
      ↓
сделать screenshot всего экрана
      ↓
сохранить его в JPEG
      ↓
снова ждать 1 секунду
```

Для захвата используется:

```python
PIL.ImageGrab.grab()
```

Путь к файлу явно не задан, поэтому JPEG сохраняется в **текущую рабочую директорию процесса**.

Например, если скрипт запущен из `tests/data_screen_capture`, новые изображения будут создаваться там.

### Для чего нужен этот скрипт

Это не часть основного алгоритма Fisher. Его назначение — **подготовка test data**.

Типичный сценарий:

```text
Запустить ESO
      ↓
Перейти в интересующее состояние
      ↓
Запустить create_new_data.py
      ↓
Получить серию screenshot-файлов
      ↓
Выбрать полезные изображения
      ↓
Положить их в tests/data_screen_capture/...
      ↓
Использовать их в тестах
```

# 2. Runtime-захват экрана

Основной production-класс находится здесь:

```text
screenCapture/screen_capture.py
```

Центральный класс:

```text
ScreeCapture
```

> Обратите внимание: имя класса в существующем проекте написано как `ScreeCapture`, а не `ScreenCapture`. Это
> существующее историческое имя и его стоит учитывать при поиске по проекту.

Класс использует `PIL.ImageGrab.grab()` для получения изображения экрана.

Упрощённо поток выглядит так:

```text
ImageGrab.grab(...)
       ↓
numpy.ndarray
       ↓
ScreeCapture.capture
```

Важное отличие от `create_new_data.py`: production-код **не обязан сохранять screenshot как JPEG**. Он получает
изображение и оставляет его в памяти, чтобы следующие компоненты могли его обработать.

---

# 3. Два изображения: `start_capture` и `capture`

В `ScreeCapture` существуют два связанных состояния:

```text
start_capture
capture
```

Их стоит не путать.

### `start_capture`

Представляет исходный screenshot, полученный на этапе начала захвата.

Исторически он также использовался как удобная точка для сохранения/диагностики исходного изображения.

В тестах и старом коде встречается закомментированная идея сохранить изображение через Pillow, например:

```python
Image.fromarray(...).save(...)
```

Это полезно, когда нужно понять, какой именно участок экрана пришёл на вход распознавателю.

### `capture`

Это рабочее изображение, которое затем может быть обрезано или обработано специализированными классами.

Таким образом, концептуально:

```text
полный screenshot
      ↓
start_capture
      ↓
обработка / crop
      ↓
capture
      ↓
parser / detector
```

# 4. Специализированный захват ESOlocate

Файл:

```text
screenCapture/eso_locate_capture.py
```

Класс:

```text
ESOLocateCapture
```

Он наследует базовую логику `ScreeCapture`, но использует её для конкретной области интерфейса ESOlocate.

После получения screenshot происходит crop нужной области.

Текущая логика содержит, в частности, срез вида:

```python
cls.capture = cls.capture[5:18, 110:190]
```

Таким образом, полный screenshot превращается в небольшой фрагмент, содержащий координаты.

Поток данных:

```text
ImageGrab.grab()
      ↓
ScreeCapture
      ↓
ESOLocateCapture
      ↓
crop координатной области
      ↓
ESOLocateParser
      ↓
(x, y)
```

### Почему это важно

Если область интерфейса ESOlocate изменится, parser сам по себе может остаться корректным, но неправильный crop приведёт
к тому, что parser больше не увидит ожидаемые цифры.

Поэтому при проблемах с распознаванием координат сначала нужно проверять:

```text
screenCapture/eso_locate_capture.py
```

и реальные размеры/позицию области на экране.

# 5. Специализированный захват компаса

Файл:

```text
screenCapture/yet_another_compass_capture.py
```

Класс:

```text
YetAnotherCompassCapture
```

Он работает по той же общей схеме, но предназначен для области компаса.

Поток:

```text
полный screenshot
      ↓
ScreeCapture
      ↓
YetAnotherCompassCapture
      ↓
crop области компаса
      ↓
YetAnotherCompassParser
      ↓
стороны света / наконечник / направление
```

Используемые parser-функции включают логику вроде:

```text
get_cardinal_directions()
get_tip()
get_compas_direction()
```

Таким образом, `YetAnotherCompassCapture` отвечает за **получение правильного изображения**, а parser — за **понимание
этого изображения**.

---

# 6. Где находятся реальные тестовые изображения

Основной каталог:

```text
tests/data_screen_capture/
```

В нём есть отдельные наборы данных.

Например:

```text
tests/data_screen_capture/locate/
```

и:

```text
tests/data_screen_capture/compass/
```

В `locate` находятся изображения, на которых проверяется распознавание координат.

В `compass` находятся изображения, отражающие разные положения компаса, например:

```text
top_3.jpeg
bottom_3.jpeg
left_3.jpeg
right_3.jpeg
...
```

Эти JPEG — не случайные изображения. Они являются **зафиксированными примерами реального состояния игры**, которые
используются для воспроизводимых тестов.

---

# 7. Как тесты используют эти изображения

Ключевой файл:

```text
tests/conftest.py
```

Он содержит fixtures и логику подготовки окружения тестов.

Смысл механизма состоит в том, чтобы заменить реальный screenshot данными из JPEG.

Упрощённо:

```text
Обычная программа

ESO
 ↓
ImageGrab
 ↓
ScreeCapture
 ↓
parser
```

а во время теста:

```text
JPEG fixture
 ↓
tests/conftest.py
 ↓
подмена capture
 ↓
parser
```

То есть parser получает практически тот же тип входных данных, который он получил бы в реальной игре, но источник
изображения под контролем теста.

---

# 8. Почему это хорошая архитектура для тестов

Такой подход даёт несколько важных свойств.

### Тесты не требуют запуска ESO

Чтобы проверить распознавание координат или компаса, не нужно:

- запускать игру;
- открывать нужный интерфейс;
- вручную ставить персонажа в конкретную точку;
- зависеть от разрешения или состояния окна во время теста.

### Тесты воспроизводимы

Один и тот же JPEG при повторном запуске даёт один и тот же вход.

Это особенно важно для image-processing кода.

### Можно хранить регрессионные случаи

Если parser когда-нибудь перестанет правильно распознавать конкретный screenshot, этот screenshot уже можно оставить в
test data и использовать как regression case.

# 10. Что делать, если нужно создать новые test images

### Шаг 1. Определить, что именно нужно проверить

Например:

```text
координаты ESOlocate
компас
особый случай распознавания
ошибочный/пограничный screenshot
```

### Шаг 2. Запустить ESO и привести UI в нужное состояние

Окно должно находиться там, где production-код ожидает соответствующий элемент интерфейса.

Особенно важно учитывать, что crop в `ESOLocateCapture` и `YetAnotherCompassCapture` зависит от координат области на
экране.

### Шаг 3. Запустить

```text
tests/data_screen_capture/create_new_data.py
```

Скрипт делает screenshot примерно каждую секунду.

### Шаг 4. Выбрать полезные JPEG

Необязательно добавлять все созданные кадры. Стоит оставить только изображения, которые представляют отдельный тестовый
сценарий.

### Шаг 5. Поместить изображения в соответствующий каталог

Например:

```text
tests/data_screen_capture/locate/
```

для координат или:

```text
tests/data_screen_capture/compass/
```

для компаса.

### Шаг 6. Добавить/обновить тест

Тест должен явно связывать конкретный входной файл с ожидаемым результатом.

Хороший тест должен позволять понять:

```text
какой screenshot → какой parser → какой ожидаемый результат
```

# 12. Отличие `create_new_data.py` от `ScreeCapture`

Это наиболее важное различие, которое легко забыть.

| Компонент                  | Назначение                  | Результат               |
|----------------------------|-----------------------------|-------------------------|
| `create_new_data.py`       | ручная подготовка test data | JPEG-файлы на диске     |
| `ScreeCapture`             | runtime-захват экрана       | изображение в памяти    |
| `ESOLocateCapture`         | выделение области координат | crop изображения        |
| `YetAnotherCompassCapture` | выделение области компаса   | crop изображения        |
| `ESOLocateParser`          | распознавание координат     | `(x, y)`                |
| `YetAnotherCompassParser`  | распознавание компаса       | направление / угол      |
| `tests/conftest.py`        | подготовка тестовой среды   | подмена runtime capture |

Если требуется **сделать новый файл изображения**, ищите `create_new_data.py`.

Если требуется **изменить, как приложение снимает экран**, ищите `screenCapture/`.

Если требуется **изменить, что тесты получают вместо реального экрана**, ищите `tests/conftest.py`.

# 13. Исторический смысл этой части проекта

Судя по структуре проекта, screenshots были введены не просто как вспомогательные картинки, а как способ стабилизировать
тестирование image-processing логики.

Вероятный жизненный цикл был таким:

```text
реальная игра
    ↓
ручной захват screenshots
    ↓
набор test fixtures
    ↓
разработка parser
    ↓
автоматические тесты
    ↓
изменения parser без необходимости запускать игру
```

Это объясняет, почему в проекте одновременно присутствуют:

- код реального screen capture;
- отдельный скрипт для создания изображений;
- папки с JPEG;
- fixtures в `conftest.py`;
- parser tests.

Все эти элементы являются частями одной цепочки.

# 14. Ограничения и потенциальные точки внимания

### Позиция областей на экране

Crop в capture-классах зависит от координат. Если UI игры, масштаб, разрешение или позиция окна изменятся, существующий
crop может перестать быть корректным.

### Формат JPEG

JPEG удобен для хранения, но является lossy-форматом. Для некоторых задач компьютерного зрения это может иметь значение.
При добавлении новых тестовых случаев стоит сохранять одинаковый подход с существующим набором данных, если нет причины
менять формат.

### Имена файлов

Лучше использовать простые ASCII-имена и понятную схему именования, чтобы ссылки и перенос репозитория между системами
не создавали проблем.

### Test fixtures должны быть понятными

При добавлении нового изображения стоит сразу документировать:

- какой сценарий оно представляет;
- что именно должен распознать parser;
- какой ожидаемый результат;
- почему это изображение нужно сохранить как отдельный test case.

# 15. Рекомендуемое улучшение на будущее

Чтобы этот механизм было проще поддерживать, стоит постепенно организовать test data по смыслу, например:

```text
tests/data_screen_capture/
├── locate/
│   ├── README.md
│   ├── normal/
│   ├── edge_cases/
│   └── invalid/
│
└── compass/
    ├── README.md
    ├── cardinal/
    ├── diagonal/
    └── edge_cases/
```

Для каждого изображения желательно иметь связь:

```text
image → test case → parser → expected result
```

Это особенно полезно при возвращении к проекту после большого перерыва.
